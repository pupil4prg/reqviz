# システム要件可視化ツール 要件定義書（v0.2）

## 1. 目的

システムの上流要件（業務特性・業務流量など）から下流設計（同時接続数、OSキャパシティ、DBコネクションプール数など）までのパラメータと、その関連性・算出根拠をグラフとして可視化する。
ルールに基づく確定的な計算・制約チェックと、AI による定性評価・提案を組み合わせ、ユーザーによる変更・承認までを一元管理する。

## 2. 前提・制約

| ID | 内容 |
|----|------|
| C-01 | サーバーは Python 標準ライブラリのみで実装する（`http.server` / `sqlite3` / `json` / `urllib` / `hashlib` / `ast` など）。サードパーティパッケージは使わない |
| C-02 | テストは pytest で行う（開発時の依存としてのみ使う） |
| C-03 | フロントエンドは Vanilla JS / HTML / CSS / SVG で実装する。外部 JS ライブラリと CDN は使わない |
| C-04 | 閉域網で動作すること。外部への通信は、設定した LLM エンドポイントへの通信だけとする |
| C-05 | データは SQLite に保存する |
| C-06 | 最終形態はチームで使う共有サーバー。MVP は単一ユーザーで運用する（§10 参照） |
| C-07 | 1システムあたりのノード（パラメータ）数は 100 以下を想定する |

## 3. 用語・データモデル

| エンティティ | 説明 | 主な属性 |
|---|---|---|
| System | 管理対象のシステム（プロジェクト） | id, name, description, template_id |
| Layer | 階層。システムごとに自由に定義し、順序を持つ | id, system_id, name, order |
| Parameter | パラメータ（グラフのノード） | id, system_id, layer_id, key（式で使う識別子）, name, type（number / string / enum / bool）, enum_options, value, unit, source（manual / formula / ai）, rationale（根拠）, ref_doc（出典）, owner, status, flags |
| Relation | パラメータ間の関連（グラフのエッジ） | id, from_param, to_param, kind（derives / constrains / influences）, note |
| Rule | ルール。種別は §5 参照 | id, system_id, kind, target_param, expression, condition, nl_text, severity, enabled |
| Template | レイヤー・パラメータ・ルールのひな形 | id, name, version, payload(JSON) |
| Revision | パラメータとルールの変更履歴 | id, entity, entity_id, before, after, actor, at, comment |
| Baseline | システム全体の版。版単位の承認と復元に使う（§6.2） | id, system_id, version_no, label, status, payload（全体の凍結コピー）, created_by, created_at, approved_by, approved_at |
| AuditLog | 承認・差し戻しなどの操作記録 | id, actor, action, target, at, comment |
| User | ユーザー（フェーズ2で本格的に使う） | id, name, role（designer / approver / admin）, password_hash |
| AiRun | AI 呼び出しの記録 | id, purpose, prompt, response, model, at |

- 式ルールの target と参照元から、Relation（derives）を自動生成する。手動の関連（influences）も登録できる
- 式の依存関係は有向非巡回グラフ（DAG）でなければならない。循環は保存時にエラーとして検出する

## 4. 機能要件

### 4.1 システム・階層・パラメータ管理
- FR-01: システムの作成・複製・削除ができる
- FR-02: レイヤーの追加・名前変更・並べ替え・削除ができる
- FR-03: パラメータの CRUD。型は number / string / enum / bool に対応する
- FR-04: 関連（エッジ）の CRUD

### 4.2 ルール管理（画面から編集）
- FR-10: 算出式・制約・条件分岐・自然言語の4種類のルールを画面上で作成・編集・有効化／無効化できる
- FR-11: 式は保存時に構文と参照先を検証する（未定義キー、型不一致、循環）
- FR-12: ルールを JSON ファイルとして書き出し・取り込みできる（Git で差分管理するため）

### 4.3 計算・検証（AI なしで動作する）
- FR-20: 上流パラメータが変更されたら、影響を受ける下流パラメータに「要再計算」フラグを付ける
- FR-21: ユーザーの指示で再計算を実行する（対象ノード単体、または下流をまとめて）。結果は「再計算案」として表示し、ユーザーが適用する
- FR-22: 制約ルールを評価し、違反したノードとルールを一覧表示し、グラフ上でも強調表示する
- FR-23: 承認済みパラメータが上流変更の影響を受けても、状態は自動で戻さない。「承認後に上流変更あり」フラグで分かるようにする

### 4.4 AI 支援
- FR-30: 入力値がルール（特に自然言語ルール）に合っているかを判定し、指摘する
- FR-31: 上流要件から、下流設計値の推奨値を提案する（式で決まらないパラメータが対象）
- FR-32: 新しいルールや関連を提案する
- FR-33: 設計根拠の文章を作る
- FR-34: AI の提案は自動では反映しない。ユーザーが採用・不採用を選び、採用した場合は source=ai として記録する
- FR-35: AI が使えないときも、FR-20〜23 は通常どおり動作する

### 4.5 ワークフロー（§6 参照）
- FR-40: パラメータ単位の状態遷移（下書き → AI評価済み → レビュー中 → 承認済み）と差し戻し
- FR-41: 承認者は1名
- FR-42: 承認・差し戻し・状態変更を監査ログに記録する
- FR-43: AI 評価はスキップできる。スキップしたことは監査ログに記録し、詳細パネルにも表示する
- FR-44: システム全体の版（ベースライン）単位でも承認を行う（§6.2）
- FR-45: 承認済みのパラメータに再計算案を適用した場合、そのパラメータは「下書き」に戻る

### 4.6 履歴
- FR-50: パラメータとルールの変更履歴を保存し、差分を表示する
- FR-51: ベースライン（版）を作成し、過去の版に戻せる（戻す操作も履歴に残す）
- FR-52: 任意の2つの版の間、または版と現在の作業状態の間で差分を表示する

### 4.7 可視化
- FR-60: レイヤーを左から右に並べたグラフを SVG で表示する（階層型レイアウトを自作）
- FR-61: ノードをクリックすると、値・単位・根拠・算出式・関連ルール・状態・履歴を詳細パネルに表示する
- FR-62: 選択したノードから上流方向・下流方向の影響範囲をたどって強調表示する
- FR-63: 状態やフラグで色分けする（違反＝赤、要再計算＝橙、承認後に上流変更あり＝紫、承認済み＝緑 など）
- FR-64: パン・ズーム、レイヤーやキーワードによる絞り込み

### 4.8 テンプレート・入出力
- FR-70: システムからテンプレートを作成し、テンプレートから新しいシステムを作成できる
- FR-73: テンプレートの内容は、システム作成時にコピーする。後でテンプレートを更新しても、作成済みのシステムには反映しない（作成元のテンプレートIDと版は記録する）
- FR-71: 出力形式は CSV（パラメータシート）、JSON（全体またはルールのみ）、HTML（設計書。グラフの SVG と根拠一覧を含む）
- FR-72: JSON の取り込み（テンプレートやルールの往復用）。Excel の取り込みは対象外

## 5. ルール仕様

| 種別 | 例 | 評価者 |
|---|---|---|
| 算出式 (formula) | `db.pool_size = ceil(app.concurrent_users * 0.2)` | Python |
| 制約 (constraint) | `db.pool_size * app.server_count <= db.max_connections` | Python |
| 条件分岐 (formula + 条件) | `0.3 if biz.type == "online" else 0.1` | Python |
| 自然言語 (nl) | 「バッチ中心の業務ではプールを小さめにする」 | AI |

- 式言語は Python の式構文のサブセットとし、`ast` でホワイトリスト方式で評価する（`eval` は使わない）
  - 許可: 数値・文字列リテラル、四則演算、`//`、`%`、`**`、比較演算、`and` / `or` / `not`、三項演算子、パラメータキー参照（`layer.key` 形式）
  - 許可する関数: `ceil` / `floor` / `round` / `min` / `max` / `abs` / `sum`
- 制約には重要度（error / warning）を設定できる

## 6. 状態遷移

### 6.1 パラメータ単位

```
下書き ──AI評価──▶ AI評価済み ──レビュー依頼──▶ レビュー中 ──承認──▶ 承認済み
  ▲                                              │                      │
  └──────────────────差し戻し─────────────────────┘                      │
  └──────────────値の変更（承認済みの値を編集した場合）─────────────────┘
```
- 「AI評価」は飛ばしてレビュー依頼に進める（スキップしたことは記録する）
- 承認済みのパラメータに再計算案を適用すると、値が変わるので「下書き」に戻る
- 状態とは独立したフラグ: `要再計算` / `制約違反` / `承認後に上流変更あり`

### 6.2 システム全体（ベースライン）単位

```
作業中 ──版の作成（凍結）──▶ レビュー中 ──承認──▶ 承認済み（確定版）
                              │
                              └──差し戻し──▶ 差し戻し済み（理由を記録）
```
- 「作業中」は、システムの現在の編集状態を指す。版を作成すると、その時点のパラメータ・ルール・関連・レイヤーをすべて凍結コピーし、ベースラインとして保存する
- 版をレビューに出す条件（満たさない場合は、理由を一覧表示して止める）:
  - すべてのパラメータが「承認済み」である
  - 重要度 error の制約違反がない
  - `要再計算` と `承認後に上流変更あり` のフラグが残っていない
- 重要度 warning の制約違反が残っている場合は、承認時のコメント入力を必須にして承認を認める
- 承認済みの版は変更できない。承認後の変更は「作業中」で行い、次の版として承認を受ける
- 最新の承認済みの版を「現行ベースライン」としてシステム一覧に表示する
- グラフビューでは、現行ベースラインと作業中の状態を比べて、変更のあったノードを強調表示できるようにする
- 版の承認・差し戻しは監査ログに記録する

## 7. AI 連携

- OpenAI 互換の Chat Completions API を `urllib` で呼び出す（LiteLLM Proxy、vLLM、Ollama などの閉域網内 LLM を想定）
- 設定項目: エンドポイント URL、モデル名、タイムアウト。API キーは環境変数（例: `REQVIZ_LLM_API_KEY`）で渡す
- 応答は JSON 形式で返させ、スキーマ検証に失敗したら破棄してエラーを表示する
- プロンプトと応答は AiRun に保存する（監査と再現のため）

## 9. 非機能要件

| ID | 内容 |
|---|---|
| NF-01 | 閉域網で動作し、静的ファイルはすべてサーバーから配信する |
| NF-02 | 100ノード規模で、グラフ描画と全体の再計算を 1 秒以内に終える |
| NF-03 | パスワードは `hashlib.pbkdf2_hmac` でハッシュ化する。セッション Cookie には HttpOnly を付け、CSRF トークンで対策する（フェーズ2） |
| NF-04 | 同時に複数人が使えるよう `ThreadingHTTPServer` を使い、SQLite は WAL モードにする。更新はバージョン番号による楽観ロックで行う |
| NF-05 | DB ファイルのコピーでバックアップできる |
| NF-06 | 主要ブラウザの最新版（Edge / Chrome）に対応する |
| NF-07 | 式評価器、再計算、制約チェック、状態遷移を pytest で網羅する |

## 10. フェーズ分け

| フェーズ | 範囲 |
|---|---|
| MVP | 単一ユーザー。§4.1〜4.8 のうち認証以外のすべて（パラメータ単位と版単位の承認を含む）。承認は自己承認を許可するが、監査ログには記録する |
| フェーズ2 | ログイン認証、ロール（設計者／承認者／管理者）、共有サーバー運用、楽観ロックによる競合検出 |

## 11. 決定事項（v0.2）

| # | 論点 | 決定 | 反映先 |
|---|---|---|---|
| 1 | 承認済みのパラメータに再計算案を適用したとき | 「下書き」に戻す | FR-45, §6.1 |
| 2 | AI 評価を必須にするか | スキップ可。スキップしたことは記録する | FR-43, §6.1 |
| 3 | 状態を管理する単位 | パラメータ単位に加えて、システム全体（版単位）でも管理する | FR-44, §6.2 |
| 4 | テンプレート更新を作成済みシステムに反映するか | 反映しない。作成時にコピーする | FR-73 |
| 5 | 版の承認時に warning の違反が残っている場合 | 承認時のコメント入力を必須にしたうえで、承認を認める | §6.2 |
