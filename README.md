# reqviz — 要件パラメータ可視化ツール

業務要件からインフラ設計までのパラメータと、その算出式・制約・関連をグラフで可視化し、
確定的な計算と AI による定性評価、変更・承認・版管理までを一元管理する Web アプリです。

パラメータ（単一の値）に加えて、実装方式の選択肢のような**列挙データ**と、テキストや JSON などの**不定形データ**も
構成項目として管理できます。画面でできる操作はすべて **REST API** から行え、同じ API を **MCP** のツールと
**A2A** の対話エージェントとしても公開しています。変更はすべて履歴に残り、過去の時点の再現・差分・復元ができます。

- 実行時の依存は **Python 標準ライブラリのみ**（`http.server` / `sqlite3` / `urllib` / `ast`）
- 画面は **Vanilla JS + SVG**（外部 JS ライブラリ・CDN なし）。閉域網で動作します
- AI は **OpenAI 互換 API**（LiteLLM Proxy / vLLM / Ollama など）を `urllib` で呼び出します

要件と設計は [docs/requirements.md](docs/requirements.md)、[docs/implementation-plan.md](docs/implementation-plan.md) を参照してください。

## 起動

```bash
uv run --no-dev python -m reqviz
```

ブラウザで http://127.0.0.1:8765/ を開くと、ログイン画面が表示されます。初回起動時に DB（`data/reqviz.db`）を作成し、
同梱テンプレート「Web三層」（`templates/web-3tier.json`）を登録します。

### ログインとアカウント

- 初回起動時に、最初の管理者アカウント（既定の ID は `admin`）を作成します。初期パスワードは自動生成して
  **起動時のコンソールに 1 度だけ表示**します（`REQVIZ_ADMIN_PASSWORD` で指定することもできます）
- アカウントを作成できるのは管理者だけです（画面右上の「ユーザー管理」）。自己登録はありません。
  管理者が決めた初期パスワードを本人に伝え、本人は最初のログイン時に必ず自分のパスワードに変更します
- 履歴と監査ログの操作者には、ログインした ID が記録されます

| ロール | できること |
|---|---|
| 設計者 | 参照・編集・再計算・レビュー依頼 |
| 承認者 | 上記に加えて、パラメータ・構成項目・版の承認と差し戻し |
| 管理者 | すべて。アカウント管理と LLM の接続設定は管理者のみ |

パスワードを忘れた場合は、管理者が「パスワード再設定」で新しい初期パスワードを設定します。

### コマンドラインからのパスワード再設定

管理者が自分のパスワードを失った場合など、画面から再設定できないときは、サーバーを動かしているマシンで次のコマンドを使います。

```bash
uv run --no-dev python -m reqviz users                          # ID・ロール・状態の一覧
uv run --no-dev python -m reqviz reset-password admin           # 新しいパスワードを 2 回入力する（画面には表示されない）
uv run --no-dev python -m reqviz reset-password admin --generate          # 自動生成して表示する
echo '新しいパスワード' | uv run --no-dev python -m reqviz reset-password admin --password-stdin   # 自動化用
```

- DB ファイル（`REQVIZ_DB_PATH`）を直接開くので、サーバーが動いていても止まっていても使えます。サーバーと同じ `REQVIZ_DB_PATH` で実行してください
- 設定したパスワードは初期パスワードになり、本人は次のログイン時に変更します。ログイン中の端末はログアウトされます
- API トークンはそのまま残ります。漏えいが疑われる場合は `--revoke-tokens` を付けると、すべて失効します
- 認証は行いません。DB ファイルを読み書きできる人だけが実行できる、という前提です。DB ファイルの権限を適切に設定してください
- 実行は監査ログに `cli:OS のユーザー名` として記録されます
- ログイン失敗が続いて一時的に止められている ID は、再設定後も解除まで最大 5 分待つ必要があります（サーバーを再起動すれば解除されます）

### 環境変数

| 変数 | 既定値 | 説明 |
|---|---|---|
| `REQVIZ_HOST` | `127.0.0.1` | 待ち受けアドレス（共有する場合は `0.0.0.0`） |
| `REQVIZ_PORT` | `8765` | ポート |
| `REQVIZ_DB_PATH` | `data/reqviz.db` | SQLite ファイル |
| `REQVIZ_AUTH` | `on` | `off` にするとログイン認証を行わない（単独利用・検証用。操作者名は自己申告になる） |
| `REQVIZ_ADMIN_USER` | `admin` | アカウントが 1 件もないときに作る、最初の管理者の ID |
| `REQVIZ_ADMIN_PASSWORD` | なし | 最初の管理者のパスワード。未指定なら自動生成して起動時に表示し、初回ログインで変更させる |
| `REQVIZ_SESSION_HOURS` | `12` | ログインの有効時間 |
| `REQVIZ_COOKIE_SECURE` | `off` | HTTPS で公開する場合は `on`（セッション Cookie に Secure 属性を付ける） |
| `REQVIZ_USER` | `designer` | 認証が無効なときの操作者名の既定値 |
| `REQVIZ_LLM_BASE_URL` | なし | 例: `http://llm-proxy.internal:4000/v1` |
| `REQVIZ_LLM_MODEL` | なし | モデル名 |
| `REQVIZ_LLM_API_KEY` | なし | API キー（環境変数のみで指定。DB・画面には保存しない） |
| `REQVIZ_LLM_TIMEOUT` | `60` | 秒 |
| `REQVIZ_AGENT_ENDPOINTS` | `on` | `off` にすると `/mcp`・`/a2a`・Agent Card を公開しない |
| `REQVIZ_PUBLIC_URL` | なし | Agent Card に載せる外向きの URL（リバースプロキシ配下など）。未指定ならリクエストの Host から決める |
| `REQVIZ_ALLOWED_ORIGINS` | なし | `/mcp`・`/a2a` で追加で許可する Origin（カンマ区切り）。既定では同一オリジンのみ |
| `REQVIZ_API_URL` | なし | stdio の MCP サーバーが使う reqviz サーバーの URL（`--url` と同じ） |
| `REQVIZ_API_TOKEN` | なし | stdio の MCP サーバーが `--url` のサーバーに渡す API トークン（`--token` と同じ） |

LLM の接続先とモデルは画面の「設定」からも変更できます。LLM が未設定でも、式による計算・制約チェック・承認・版管理はすべて使えます。

## 使い方の流れ

1. **システム作成**: テンプレートから作成すると、レイヤー・パラメータ・ルールがコピーされます
2. **関連図**: 上流（左）から下流（右）へのつながりを確認。ノードをクリックで詳細、Shift + クリックで影響範囲
3. **値の変更**: 上流の値を変えると、下流に「⟳ 要再計算」、承認済みの下流に「▲ 承認後に上流変更」が付きます
4. **再計算**: 「再計算」で再計算案を作成し、確認してから適用します（承認済みの値は下書きに戻ります）
5. **AI 支援**: 妥当性評価・値の提案・ルールの提案・根拠の作成。提案は採用するまで反映されません
6. **承認**: 下書き → AI評価済み（スキップ可） → レビュー中 → 承認済み。差し戻しにはコメントが必要です
7. **版管理**: 全パラメータが承認済みで error 違反がなければ版を作成できます。warning が残る場合は承認時にコメントが必要です
8. **書き出し**: 設計書（HTML）、パラメータシート（CSV）、全体／ルールのみ（JSON、Git での差分管理向け）

## パラメータの別名

パラメータには、参照名（`レイヤーキー.キー`）と名前のほかに、別名をいくつでも登録できます。
設定ファイル上のパラメータ名（実装名）や、日本語の論理名、旧名などを想定しています。

- 関連図の詳細パネルの「定義を編集」、またはパラメータ追加のダイアログで登録します。種類（実装名・論理名など）は自由に付けられます
- 関連図とパラメータ一覧の検索は、別名も対象にします
- `GET /api/systems/{id}/params/lookup?name=`（MCP では `lookup_params`）で、参照名・キー・名前・別名のいずれかに完全一致するパラメータを引けます。
  別名は一意でなくてもよいので、一致したものをすべて返します
- 別名は履歴・版・テンプレート・JSON 書き出し・CSV・設計書に含まれます。別名の変更では承認状態は変わりません
- ルールの式から参照できるのは、これまでどおり参照名だけです

## 環境ごとの管理

本番・検証・開発のように、環境ごとに値が異なる構成を管理できます。

- 「環境」タブで環境を追加すると、今のシステムの構成と値をコピーした環境ができます。上部の環境名から、同じ画面のまま切り替えられます
- **値・承認・版・履歴は環境ごとに独立**です。同じ算出式を環境ごとの値で計算し、本番の版 v3 と開発の版 v7 のように別々に版を重ねられます
- **比較**: パラメータ・構成項目・ルールを環境の間で並べ、値の違い・その環境にない項目・定義の食い違いを示します
- **構成の同期**: ある環境の定義（レイヤー、パラメータの名前・型・単位・別名・所属、選択肢の候補、ルール、関連、コンポーネント）を他の環境にそろえます。
  値・採用案・本文・根拠・タグは反映先のものを保ち、値が変わらない項目は承認も保ちます。実行前に差分を確認できます
- **値のコピー**: 選んだ項目の値・採用案・本文を、別の環境に写します（開発で決めた値を本番に反映する、など）。反映先では通常の変更として下書きに戻ります

| API | 内容 |
|---|---|
| `GET/POST /api/systems/{id}/environments` | 環境の一覧・追加（MCP: `list_environments` `create_environment`） |
| `GET /api/systems/{id}/environments/compare` | 環境の比較（MCP: `compare_environments`） |
| `POST /api/systems/{id}/environments/sync` | 構成の同期。`preview: true` で差分のみ（MCP: `sync_environment_structure`） |
| `POST /api/systems/{id}/environments/copy-values` | 値のコピー（MCP: `copy_environment_values`） |
| `PUT/DELETE /api/systems/{id}/environment` | 環境名の変更・グループから外す |

環境は内部的には 1 環境 = 1 システムで、同じシステムの環境違いを「環境グループ」で束ねています。そのため定義の変更は自動では他の環境に伝わらず、
「構成を同期」で明示的に反映します。パラメータの参照名（レイヤーやキー）を変えた場合、同期では別の項目として扱われ、反映先の値は引き継がれません。

## コンポーネントと依存関係

レイヤーが設計工程（業務要件 → … → インフラ設計）の軸なのに対して、コンポーネントは AP サーバー・ミドルウェア・OS のような構成要素の軸です。
パラメータと構成項目は、レイヤーとは別にコンポーネントを 1 つ持てます（未設定でも構いません）。

- 「コンポーネント」タブでコンポーネントを作成し、パラメータ一覧の一括操作「コンポーネントを設定…」などで割り当てます
- **依存関係「A → B」は、A の設計が B に波及すること**を表します（例: ミドルウェア → OS）。向きごとに定義でき、説明を付けられます
- 定義した依存は、式・制約・関連による実際のつながりと突き合わせて確認できます
  - 裏付けとなるつながり（どのルールで、どのパラメータ同士がつながっているか）を表示します
  - つながっているのに依存として定義されていない組を「定義されていないつながり」として挙げ、その場で定義できます
  - 依存の循環、コンポーネントが未設定の項目も表示します
- 依存に「変更を知らせる」を設定すると、波及元のパラメータや採用案が変わったとき、波及先コンポーネントの承認済みパラメータに
  「承認後に上流変更」が付き、承認画面で確認を求めます（算出式でつながっていなくても確認を促せます）
- 関連図・パラメータ一覧はコンポーネントで絞り込めます。コンポーネントと依存は、版・テンプレート・JSON 書き出し・設計書に含まれます

| API | 内容 |
|---|---|
| `GET/POST /api/systems/{id}/components`、`GET/PUT/DELETE /api/components/{id}` | コンポーネント |
| `GET/POST /api/systems/{id}/component-deps`、`PUT/DELETE /api/component-deps/{id}` | 依存関係 |
| `GET /api/systems/{id}/components/analysis` | 依存の分析（MCP: `analyze_components`） |
| `POST /api/systems/{id}/components/assign` | 項目をまとめて割り当て（MCP: `assign_component`） |

## タグと検索

パラメータと構成項目には、自由な文字列のタグを付けられます。「開発中」「要確認」「確定」のような作業状況の管理や、分類に使えます。

- タグは、関連図の詳細パネル・パラメータ一覧・構成項目の編集画面で付けます。パラメータ一覧では、選択した行にまとめて付け外しできます
- タグは承認の状態（下書き → 承認済み）とは独立です。タグを変えても承認状態は変わりません（履歴には残ります）
- 「検索」タブで、パラメータと構成項目を横断して探せます。語（空白区切りで AND）とタグ・種類・状態を組み合わせられ、
  参照名・名前・別名・値・根拠・出典・担当・タグ・選択肢・本文が対象です。検索条件は URL に残るので、そのまま共有できます
- 関連図とパラメータ一覧でも、タグで絞り込めます
- 「検索」タブの「タグ名を変更」で、システム全体のタグ名をまとめて変えられます（既にあるタグ名にすると統合されます）

| API | 内容 |
|---|---|
| `GET /api/systems/{id}/search?q=&tags=&tag_mode=&kind=&status=&layer=` | 横断検索（MCP: `search`） |
| `GET /api/systems/{id}/tags` | 使われているタグと件数（MCP: `list_tags`） |
| `POST /api/systems/{id}/tags/apply` | 複数の項目にタグをまとめて付け外し（MCP: `apply_tags`） |
| `POST /api/systems/{id}/tags/rename` | タグ名の変更（MCP: `rename_tag`） |

## 構成項目（列挙データ・不定形データ）

「構成項目」タブで、パラメータでは表せない構成情報を管理します。参照名はパラメータと同じ `レイヤーキー.キー` です。

| 種別 | 内容 | 例 |
|---|---|---|
| 選択肢（`choice`） | 候補の一覧（説明・長所・短所・任意の属性）と、採用した候補 | セッション管理方式: sticky / redis / db |
| 不定形データ（`document`） | テキスト・Markdown・YAML・任意の JSON | ネットワーク構成メモ、sysctl の設定一式 |

- 選択肢の採用案は、ルールの式から `app.session_store == 'redis'` のように参照できます（代入先にはできません）。
  採用案を変えると、それを参照する下流のパラメータに「要再計算」が付きます
- 状態は 下書き → レビュー中 → 承認済み。内容（候補・採用案・本文）を変えると下書きに戻ります
- 版（ベースライン）・テンプレート・JSON 書き出し／取り込み・設計書（HTML）に含まれます。未承認の構成項目があると版は作成できません

## 履歴管理

パラメータ・構成項目・ルールの変更は、変更前後の内容・操作者・コメントつきで 1 件ずつ記録されます
（JSON 取り込み、版からの復元、テンプレートからの作成のような一括操作も、項目ごとに記録します）。

| できること | 画面 | API |
|---|---|---|
| 1 項目の版の系列（名前変更もさかのぼる） | 構成項目の「履歴」、関連図の詳細パネル | `GET /api/systems/{id}/history/timeline?entity=&key=` |
| 過去の時点の内容を再現 | ― | `GET /api/systems/{id}/history/state?at=` |
| 2 時点間の差分 | 履歴 →「時点間の差分」 | `GET /api/systems/{id}/history/diff?from=&to=` |
| 1 項目を過去の内容に戻す | 履歴 →「復元」 | `POST /api/revisions/{id}/restore` |
| 全体を版の内容に戻す | 版管理 →「復元」 | `POST /api/baselines/{id}/restore` |

時点は ISO 8601 の日時か `rev:<リビジョンID>` で指定します。承認・差し戻しなどの状態の変化は監査ログに残ります。

## API・MCP・A2A

すべて同じサーバー（既定 http://127.0.0.1:8765 ）で提供します。詳細は [docs/agent-integration.md](docs/agent-integration.md)。

| 入口 | 場所 | 用途 |
|---|---|---|
| REST API | `/api/...`（`GET /api` でルート一覧） | 画面と同じ全操作 |
| MCP（Streamable HTTP） | `POST /mcp` | REST API をツールとして公開。プロトコル 2026-07-28 と、`initialize` を使う 2025-11-25 / 2025-06-18 / 2025-03-26 |
| MCP（stdio） | `uv run --no-dev python -m reqviz.mcp [--url URL]` | 同上。`--url` なしなら DB を直接開く |
| A2A（JSON-RPC） | `POST /a2a`、Agent Card は `/.well-known/agent-card.json` | A2A 1.0。文章での対話（LLM 設定時）と、ツールの直接指定 |

プログラムやエージェントから使うときは、画面の「設定」で発行した **API トークン**を `Authorization: Bearer <トークン>` で渡します
（MCP と A2A は API トークンが必須）。操作はトークンの持ち主の ID とロールで行われます。

A2A の対話では、データを変更する操作の前にエージェントが内容を示して確認を求めます（タスクは `TASK_STATE_INPUT_REQUIRED` になり、
同じタスクに「はい」と返すと実行）。呼び出し側が責任を持つ場合は、リクエストの `metadata.autoApprove = true` で省略できます。

## ルールの書き方

| 種別 | 例 |
|---|---|
| 算出式 | `ceil(biz.peak_tps * biz.avg_response_sec * nfr.safety_factor)` |
| 条件分岐 | `0.5 if biz.business_type == 'online' else 0.2` |
| 制約 | `db.pool_per_server * app.server_count + db.reserved_connections <= db.max_connections` |
| 自然言語 | 「バッチ中心の業務では、DB のプール数を抑えること」（AI の評価基準） |

参照は `レイヤーキー.パラメータキー`。使える関数は `ceil floor round min max abs sum`。
式は `ast` によるホワイトリスト方式で評価します（`eval` は使いません）。

## 開発

```bash
uv sync
uv run pytest
```

構成:

```
reqviz/
  engine/     式評価・依存グラフ・再計算・制約・レイアウト（DB 非依存の純粋関数）
  repo/       DB 読み出し、変更履歴・監査ログ
  workflow/   編集・再計算の適用・状態遷移・版・テンプレート・スナップショット
  ai/         OpenAI 互換クライアント、プロンプト、ジョブ、提案の採用
  io/         CSV / HTML 書き出し
  api/        REST API のルーティング
  auth.py     ログイン認証（パスワード、セッション、API トークン、アカウント管理）
  agent/      ツール定義（REST API への対応表）と対話エンジン。MCP と A2A が共有する
  mcp/        MCP サーバー（プロトコル処理、stdio の入口）
  a2a/        A2A サーバー（Agent Card、JSON-RPC、タスクの保存）
  static/     画面（Vanilla JS / SVG）
templates/    同梱テンプレート
tests/        pytest（engine / workflow / api / ai / agent）
```

## 制限

- 承認者・管理者は、自分が編集した項目を自分で承認できます（監査ログには記録されます）
- 通信の暗号化は行いません。共有サーバーで使う場合は、HTTPS を終端するリバースプロキシを前段に置き、`REQVIZ_COOKIE_SECURE=on` にしてください
- ログイン失敗の回数制限（5 回で 5 分）はプロセス内で数えるため、再起動で解除されます。コマンドラインからは解除できません
- MCP の認証は固定の API トークンです（MCP 仕様の OAuth による認可には未対応）
- MCP が提供するのはツールのみです（resources / prompts、SSE によるストリーミング応答、`subscriptions/listen` は未対応）
- A2A はストリーミング（`SendStreamingMessage`）とプッシュ通知に未対応です。reqviz から他のエージェントを呼び出す機能もありません
- コンポーネントは 1 階層です（入れ子にはできません）。1 つの項目が所属できるコンポーネントは 1 つです
- 選択肢項目は、関連図にはノードとして表示されません（式からの参照と要再計算の伝播は働きます）
- 過去の時点の再現は内容（値・候補・本文・式）が対象です。v0.1 で行った一括操作（取り込み・版からの復元）より前の時点は正確に再現できません
